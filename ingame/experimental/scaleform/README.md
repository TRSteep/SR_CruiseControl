# Scaleform — экспериментальный прототип нативной строки

Отдельный диагностический ASI. Не содержит управления газом и не рисует DirectX-наложение. Версия 5 по умолчанию только наблюдает за созданием Flash-объектов и собственными чтениями HUD игрой. При `EnableTestRow=1` пытается создать TEST после штатного чтения `brakeBtn`, а не из callback создания HUD. Эта новая схема собрана и проверена автономными тестами, но в игре ещё не проверялась. Предыдущая схема версии 2 вызвала зависание/сбой; точная причина пока не установлена.

Поддерживает только EXE с SHA256 `a3cb442ec138eb2eb7e335e5c80e376766550740e49e233ac9eace035e182285` (исследуемая Epic 44.1). Перед установкой перехватов проверяет весь EXE и префиксы обеих функций. При несовпадении записывает причину в журнал и ничего не перехватывает.

## Сборка и проверка

Из корня репозитория:

```powershell
.\ingame\experimental\scaleform\build.ps1
```

Для сборки отдельного ZIP используйте `build.ps1 -Package`. Архив `ingame/build/scaleform-probe/SnowRunner-Scaleform-Prototype-v5.zip` содержит ASI, INI с выключенным TEST, инструкцию и лицензию MinHook. Скрипт сборки ничего не устанавливает и не запускает игру.

Выход: `ingame/build/scaleform-probe/SnowRunnerScaleformProbe.asi`. Сборка запускает проверки чтения строк, недоступных адресов, передачи всех аргументов/результатов и неизменности наблюдаемых значений.

При закрытой игре скопируйте ASI и `SnowRunnerScaleformProbe.ini` рядом с SnowRunner.exe; нужен уже установленный ASI-загрузчик. С `EnableTestRow=0` мод только собирает журнал, без TEST. Чтобы позднее проверить нативную строку, поменяйте значение на `1` и перезапустите игру. Выберите «Продолжить» и дождитесь вида машины с автомобильным HUD. Достаточно стоять на месте. Строка TEST при успешном создании находится на два шага выше ручника, над рабочей планкой автопилота.

Если игра вообще не вызывает GetMember для `brakeBtn`, попытки создания не будет: после сообщения `TEST-await-brake-read` в журнале не появится `TEST-result`. Это означает, что потребуется другая точка подключения; отсутствие TEST само по себе не доказывает ошибку построения.

Журнал: `SnowRunnerScaleformProbe.log` рядом с EXE. После диагностики закройте игру и удалите `SnowRunnerScaleformProbe.asi` и `SnowRunnerScaleformProbe.ini`; рабочий мод и загрузчик сохраняются. На лету DLL не выгружать.

Журнал содержит имена Flash-символов, идентификаторы потоков и адреса объектов только текущего процесса. Адреса действительны лишь в пределах одного запуска. Игровые объекты и ссылки между событиями не удерживаются. Запись файла выполняется выделенным потоком; обработчики публикуют ограниченную очередь событий. Размер очереди — 4096 событий, после её заполнения новые записи пропускаются. Строки ограничены 127 символами; остальные игровые данные не записываются.

## Точки наблюдения и доказательства

Это RVA относительно загруженного SnowRunner.exe; они не считаются совместимыми с другими сборками.

- `0x10243A0`: игровая фабрика/инициализация Flash-объекта. Найдена по ссылке на диагностику `Create flash object with linkageName...`. Реальный вход восстановлен по цепочке Windows unwind metadata: запись `0x10245C2` — внутренний фрагмент, а не вход. Входные аргументы: owner и игровая строка linkage. После оригинального вызова читается значение owner+0x58. RAX передаётся обратно без изменения.
- `0x1B61880`: создание дочернего символа через ObjectInterface. Вызов из `0x1082408` передаёт interface, parent, output, linkage, instance, depth=-1, init=null. Имя экземпляра формируется как `do%d_%s`. Соседняя ветка вызывает создание пустого `flash.display.Sprite` через `0x1B61560`. Это подтверждает существование игрового пути создания display objects в AS3; само по себе не гарантирует, что символ из hud_lib доступен любому Movie.
- Наблюдаемое значение занимает 48 байт: два служебных слова, interface+0x10, type+0x18, object+0x20, auxiliary+0x28. Это установлено из кода копирования/освобождения, а не взято из произвольной версии SDK. Observer только читает его через ReadProcessMemory и не вызывает refcount-функции.
- Дополнительные точки для TEST: GetMember `0x1B5D4B0`, SetMember `0x1B5D870`, Invoke `0x1B5DCB0`, Release `0x1B5D0F0`, CreateEmptyMovieClip/Sprite `0x1B61560`. Адреса связаны с тем же строгим хешем EXE; перед запуском также сверяются префиксы функций.

В режиме TEST временные значения освобождаются в том же UI-потоке, где созданы; управляемые ссылки между кадрами не сохраняются. Существование строки проверяется через `getChildByName`, при неудаче построения строка удаляется через `removeChild`. В частности проверены тестами отсутствие повторного создания, освобождение временных ссылок и откат частичной сборки.

`kind=3` сообщает `TEST-disabled`, `TEST-await-brake-read` или `TEST-result`. У последнего поле `type` обозначает этап: 1 — нет панели; 2 — нет ручника; 3 — не получены координаты; 4 — строка уже существует; 5 — не создан контейнер; 6 — ошибка сборки и попытка отката; 7 — строка создана. `kind=4` записывает собственные вызовы GetMember игрой для `rightHudPanelContainer`, `brakeBtn`, `wdBtn`, `diffBtn`, `gearBox` и их результат. В режиме наблюдения поле `ok` у `kind=1` не используется; успех присоединения символа отражает `kind=2`.

`kind=5` — контрольные точки собственных UI-операций: `UI-get.begin/end`, `UI-set.begin/end`, `UI-invoke.begin/end`, `UI-sprite.begin/end`, `UI-attach.begin/end`, `UI-release.begin/end`. Поле `instance` содержит имя свойства, метода или символа, поле `ok` у `.end` — результат. Последняя `.begin` без соответствующей `.end` помогает локализовать незавершённый вызов. Очередь обрабатывается фоновым потоком раз в 250 мс; при мгновенном завершении процесса последние события могут не попасть на диск.

Полный разбор и границы достоверности: `docs/scaleform-integration-analysis.md`.

## Следующий рубеж

Первый запуск подтвердил работу обоих перехватов и успешное создание AS3-символов игрового интерфейса на одном потоке (в частности `DefaultMouseCursor`, `in_game_layer`, `hud_interaction_option`). Он завершён до загрузки автомобильного HUD, поэтому наличие TEST ещё не подтверждено.

Второй запуск подтвердил успешное создание `defaultHud`, причём его создал другой поток, чем меню первого этапа. Вызов цепочки построения TEST сразу после этой фабрики не завершился; пользователь подтвердил зависание/сбой. Точный сбойный вызов не локализован, поэтому нельзя считать подтверждёнными ни достаточную готовность HUD в этом callback, ни весь восстановленный ABI. Все дополнительные входы в VM из этого callback удалены. Версия 3 наблюдает GetMember, не вызывает его самостоятельно.

Версии 4 и 5 подготовлены без нового запуска игры по просьбе пользователя. Собственные UI-операции выполняются только при явно включённом TEST, синхронно после успешного штатного чтения ручника. Есть защита от рекурсии и повторных попыток на том же родителе; между вызовами сохраняется лишь числовой идентификатор попытки, а не удерживаемая ссылка. Без проверки в игре эта точка остаётся кандидатом, а не подтверждённой безопасной интеграцией.

При возобновлении тестирования нужны журнал штатных чтений панели и результат TEST, затем проверка движения и жизненного цикла. Только после этого подключать состояние автопилота. Записанные адреса не использовать после удаления объекта или в другом запуске. Собственные UI-операции из потока журнала или callback создания HUD запрещены.
